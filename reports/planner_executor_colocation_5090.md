# 规划器与执行器同卡共置：Qwen3.8-27B 规划器 + ImageWAM 执行器（RTX 5090，FlashRT）

问题：一个 27B 的 VLM 规划器和一个 20 Hz 的 WAM 执行器放在同一块 32 GB 的 RTX 5090 上、都用 FlashRT 推理时，执行器在哪里丢截止期，经过哪种资源（主机侧发射路径、SM、显存带宽、显存容量、功耗），每种保护手段让规划器付出多少。原始数据、脚本和完整表格在 `research/experiments/colocation_qwen27b_5090/`（`README.md`、`report_tables.md`、`cells_summary.md`）；相关系统文献在 `research/reports/gpu_sharing_colocation_literature.md`。

## 0. 结论

本节第 1–4 条、3.1–3.2 节和第 4 章是 cuBLAS 13.4.1.3 下的测量（执行器单独 28.2–28.8 ms）。在 cuBLAS 13.6.1.10 下（执行器单独 24.7 ms，规划器单独 0.66 / 1.32 s）重测了 8 个同进程配置的修复前后，见 3.3 节：修复后同进程 green context（规划器 88 个 SM）短、长上下文执行器 p99 40.6 / 40.8 ms、错过 0%，规划器 0.98 / 2.35 s（1.49 / 1.78 倍）；修复前同一配置错过 83.0% / 85.4%。

1. 同一进程里共置时，执行器丢截止期的主因在主机侧，而不在 GPU 上。规划器每个推测周期有一次读回（`fvk.cuda_read_i32_sync`）在持有 GIL 的情况下等整个验证前向；长上下文的分块 prefill 是 Python 循环逐个发射 kernel。两者让执行器线程拿不到 GIL，stream 优先级和 green context 的 SM 划分都失效，执行器错过 80–92% 的截止期。
2. 只把那一次读回改为在 GIL 之外等待，同进程 + 执行器高优先级 stream 的短上下文就从错过 84.8% 变为 0%；再把长上下文 prefill 改为 CUDA graph 回放，同进程 + green context（规划器 48 个 SM）的长上下文也从错过 88.1% 变为 0%（p99 35.9 ms），规划器一次调用 2.29 倍，好于两进程 MPS 25% 的 2.58 倍。
3. 主机侧问题去掉后，剩下的是 GPU 上的资源分配：
   - 不限 SM 时，长 prefill 会占满 SM，执行器仍错过 44%；
   - 限住规划器的 SM 就能守住截止期，代价主要落在规划器的 prefill（首 token 慢 2.4–3.3 倍）。同进程 green context 与两进程 MPS 给出相近的权衡：规划器 50% SM 时，长上下文规划器 1.80× / 1.55×（green50 / mps50），执行器 p99 44.6 / 47.0 ms；
   - 短上下文以解码为主，规划器从 48 个 SM 加到 88 个 SM 几乎不变快（1 050 → 1 036 ms，prefill 快了，解码因带宽争用慢了）；
   - SM 隔离之后还剩显存带宽干扰：在 5090 上让执行器慢 1.07–1.20 倍；用纯拷贝负载把带宽打满时可达 1.85–3.0 倍，在 Thor 上会是主要问题。
4. 显存容量和功耗是硬约束：
   - 27B 规划器加执行器只有在执行器丢掉文本编码器和 FP16 权重后才装得下；
   - 两个模型同时跑时功耗贴近 575 W 上限，SM 频率降 1–9%。
5. 按 VoLoAgent harness 的调用频率回放（3.4 节）：monitor 每 80 步一次、执行器每 533 ms 一个动作块时，规划器跟得上，执行器在 prio 下几乎不受影响（超过一个控制步的比例 0–0.7%，没有一次超过一个动作块），规划器只慢 1–3%；同步协议下规划器让机器人停顿仿真时间的 27–31%。剩下的问题在规划器的服务路径上：没有 EOS 停止（按 `max_tokens` 512 解码时一次 monitor 11 s）、多数调用要现场捕获 graph（第一次 monitor 3.3–3.8 s）、执行器换指令所需的文本编码器装不下。MTP 推测解码在补上草拟头的 prompt 尾部之后，monitor 的解码快 2.1–2.3 倍（3.5 节）。
6. 对 harness 的负载，具体的优化目标是规划决策的生效延迟：从一次调用到期到执行器按其结果行动的时间，约束是执行器不超过截止期（第 7 章）。它在 prio 下的 p50 为 18 / 21 步，可拆成 ViT + prefill、解码、运行中的 graph 捕获、执行器换指令和共置干扰几个分量；换指令在 5090 上共置时没有通路。

## 1. 设置

| 项 | 取值 |
|---|---|
| GPU | RTX 5090 32 GB（可用 31.36 GiB），功耗上限 575 W，频率不锁（实测 2.6–2.9 GHz）；每个实验点运行期间没有其他用户的 GPU 进程（每 2 s 检查） |
| 执行器 | ImageWAM LIBERO（FLUX.2 klein 4B + ActionDiT），FlashRT fp8，10 步去噪，两路 224×224 相机；一次推理 = 输入暂存 + 一张 5 240 个 kernel 的 CUDA graph（VAE、prefill、去噪）；单独运行 28.6–28.8 ms（cuBLAS 13.4.1.3；13.6.1.10 下 24.2 ms） |
| 执行器节拍 | 周期 50 ms（20 Hz）；延迟 = 完成时刻 − 释放时刻；超过 50 ms 记为错过截止期，并推迟下一次释放 |
| 执行器显存 | `set_prompt` 后释放 Qwen3-4B 文本编码器和 140 个量化层的 FP16 源权重：22.96 → 6.30 GB；释放后、以及把释放的显存填满 NaN 后，输出动作逐位不变 |
| 规划器 | Qwen3.8-27B 蒸馏模型，FlashRT NVFP4，FP8 KV，分块 prefill，MTP 推测解码，关闭 thinking；输入 = 前视 + 腕部两帧 LIBERO 图像（各 256 个图像 token）+ 规划指令（要求 JSON 输出），每次生成 64 个 token |
| 规划器上下文 | 短：602 token；长：8 110 token（同一提示词前加一段文本执行历史） |
| 规划器频率 | 背靠背连续调用（最坏情况） |
| 测量窗口 | 每个实验点 60 s；nvidia-smi 每 100 ms 采样（利用率、显存利用率、SM / 显存频率、功耗）；每个 tick 分段计时（输入暂存 / graph 发射 / 等待完成） |

共享方式：

| 方式 | 机制 |
|---|---|
| `serial` | 同一线程，规划器调用跑完才轮到执行器 |
| `prio` | 同一进程两个线程，执行器 stream 优先级最高 |
| `green<P>` | 同一进程，CUDA green context 把 P% 的 SM 分给规划器（25% → 48 个 SM，50% → 88 个 SM），执行器用其余 SM |
| `process` | 两个进程，驱动时间片轮转 |
| `mps<P>` | 两个进程在 MPS 下，规划器限 P% 的线程，执行器限 100−P%（`mps100` 不限） |
| `coop` | 同一进程，规划器只在执行器空闲、且下一段 GPU 工作（ViT、256 token 的 prefill 分块、一个解码周期）在下一次释放前放得下时才启动；放不下的工作段在空闲窗口一开始启动 |

主机侧的三个修改只用于 `prio`、`green`、`coop` 的对照组：

- 读回不占 GIL：每周期读回接受数之前，先在 GIL 之外同步 stream 等 GPU，再拷贝。
- graph 捕获改为线程局部模式：避免另一线程的 CUDA 调用使规划器临时捕获的 graph 失效。
- 长上下文 prefill 用 CUDA graph 回放：使用前端已有的 `FLASHRT_QWEN36_TQ_PREFILL_GRAPH=1` 开关。

前两项最初以实验脚本里的补丁验证，现已并入 FlashRT（`cuda_read_i32_sync` 绑定，Qwen3.6、ViT、ImageWAM 前端的全部 graph 捕获）。只用框架修复、关掉补丁重测，第 3 节各行全部复现：p99 相差 0.1–1.3 ms，错过率相同。绑定若先排队拷贝再同步，拷到 pageable 内存的这次拷贝会在驱动里等前面的 GPU 工作，期间卡住另一个线程的发射（执行器发射从 14 ms 变成 37.5 ms，错过 92.4%），所以要先同步再拷贝。

- 一次调用里解码占大头：短上下文 596 / 666 ms，长上下文 642 / 1 334 ms；每次调用 23–25 个推测周期（每周期接受约 2.6–2.8 个 token）。
- ViT 和 prefill 随 SM 数变化，48 个 SM 时慢 2.4–2.6 倍；解码几乎不随 SM 数变化，只用 28% 的 SM，每周期只慢 16%。
- 推算的解码带宽需求：每个推测周期读 17.5–20.6 GB 权重（验证前向 14.45 GB，加 K 次 MTP 草稿各 1.03 GB，K = 3–6；由 checkpoint 张量形状和运行时格式算出），按每周期 23.8–27.9 ms 约 0.74–0.87 TB/s；同卡 1 GiB 设备拷贝实测 1.52 TB/s。

### 3.4 按 VoLoAgent harness 的调用频率回放

工作负载是 VoLoAgent Full loop（subgoal 模式，VLM 失败监视，`replan_tools`，每 80 个环境步检查一次，带前置相机）在 LIBERO-10 第 0、43、188 个 episode 上的规划器调用；调用内容先由同一规划器录制一遍（贪心，不开 thinking），回放时解码到录制回复的 EOS 为止。每个 episode 800 步（15 Hz，仿真 53.3 s）：第 0 步一次 decompose（3 张图），之后每 80 步一次 monitor（共 10 次；6 张图：前后两个时刻 × 前置 864×480、外部 1280×720、腕部 224×224 或 1280×720），monitor 返回 replan 或在最后一个子任务上返回 next 时 replan（6 段录制里只出现 1 次）。monitor 输入 4 079 / 5 711 个 token（腕部 224 / 1280×720），输出 38–87 个 token。执行器每 8 步（533 ms）推理一次，单独 24.5 ms（cuBLAS 13.6.1.10）。

- sync：harness 的同步协议，一个线程，有规划器调用的那一步先跑完调用再推理执行器。
- realtime：按墙钟回放，执行器每 533 ms 释放一次，每次调用在第 step / 15 s 到期，两者并发；共享方式 prio / green50 / coop，同 3.1 节。

| 方式 | 腕部 | 每 episode 墙钟 s | 规划器 s / episode | monitor p50（热）ms | monitor 最长 ms | 决策延迟最长（步） | 执行器 p50 / p99 / 最长 ms | 超过 1 步（66.7 ms） | 回复与录制一致 |
|---|---|---|---|---|---|---|---|---|---|
| sync | 224 | 17.1 | 14.5 | 1 157（1 020） | 3 338 | — | 24.6 / 24.8 / 25.4 | 0% | 33/33 |
| sync | 720 | 19.0 | 16.4 | 1 345（1 168） | 3 666 | — | 24.5 / 24.8 / 24.9 | 0% | 33/33 |
| prio | 224 | 54.4 | 14.9 | 1 190（1 035） | 3 434 | 51.7 | 25.4 / 35.2 / 47.6 | 0% | 33/33 |
| green50 | 224 | 54.7 | 18.3 | 1 479（1 321） | 4 037 | 60.8 | 33.4 / 74.7 / 101.5 | 1.3% | 33/33 |
| coop | 224 | 54.6 | 17.0 | 1 409（1 226） | 3 554 | 53.5 | 25.5 / 26.7 / 29.3 | 0% | 4/33 |
| prio | 720 | 54.3 | 16.8 | 1 361（1 202） | 3 788 | 57.1 | 25.5 / 49.5 / 98.2 | 0.7% | 33/33 |
| green50 | 720 | 54.6 | 21.4 | 1 765（1 586） | 4 589 | 69.1 | 33.4 / 175.0 / 303.6 | 1.7% | 33/33 |
| coop | 720 | 54.4 | 19.7 | 1 734（1 461） | 3 537 | 53.4 | 25.3 / 26.7 / 30.8 | 0% | 4/33 |

- sync 下每个 episode 的模型时间是 17.1 / 19.0 s，其中规划器 14.5 / 16.4 s，机器人要停顿仿真时间的 27–31%；执行器一共只用 2.5 s。
- realtime 下规划器跟得上：每次调用都在下一次到期（80 步 = 5.33 s 之后）前返回；墙钟比仿真时间多出的 0.1–1.9 s 是第 800 步那次 monitor 在最后一次执行器推理之后才结束。
- harness 的执行器要求比 3.1–3.3 节的 50 ms 周期宽得多：8 个格子里没有一次推理超过一个动作块（533 ms）；超过一个控制步（66.7 ms）的比例 prio 0–0.7%，green50 1.3–1.7%（执行器只有一半 SM，p50 33.4 ms），coop 0%。
- 规划器的代价（monitor p50 相对 sync）：prio 多 1–3%，coop 多 22–29%，green50 多 28–31%。在这个频率下 prio 是规划器最便宜、执行器也守得住的选择。
- 大多数调用是冷的：每格 29–30 次 monitor 里有 23–26 次要现场捕获 graph（中位 5–6 个，多约 0.2 s）；进程里第一次 monitor 要捕获 56–59 个 graph，耗时 3.3–3.8 s，决策延迟的最大值（52–69 步）都是这一次。
- coop 的回复和录制不一致，原因是 coop 需要的 256 token prefill 分块，而不是共置：规划器单独运行、只换成 256 分块时，第 0 个 episode 的 11 次调用中 8 次回复改变，其中一次 monitor 的决策从 `in_progress / continue` 变为 `complete / next`；默认分块的 eager prefill 11 次全部一致（`issues.md` ISSUE-110）。回放按录制的长度解码，计时仍可比。
- 执行器换指令：文本编码器常驻时 `set_prompt` 约 30 ms，遇到新的上下文长度要再捕获一张 graph，共约 240 ms；进程里第一次 751 ms。Qwen3-4B 编码器 7.6 GB，而规划器常驻时每格只剩 2.6–3.0 GB，装不下。
- `generate` 没有 EOS 停止，按 `max_new_tokens` 解码完再截断：用 harness 的 `max_tokens` 512 时，一次 monitor 要 11.2–11.4 s，decompose 16–17 s（`opportunities.md` OPT-040）。

### 3.5 规划器的 MTP 推测解码

合并后的规划器 checkpoint 里没有 MTP 权重，草拟头用的是官方 Qwen3.8-27B-FP8 发布版的 MTP 头（按未微调的原版模型训练）。RTX 的长上下文路径在 prefill 之后用 prompt 的尾部行（默认按长度查表：monitor 512 行，decompose 2 048 行）填充草拟头的 K/V，草拟头由此看到 prompt；关掉尾部时草拟头只看到已生成的 token。

下表在 3.4 节录制的 22 次调用（ep0、ep43，腕部 224）上测量，K = 3，尾部 fc 投影用 cuBLASLt。两种主模型用同一个转换脚本得到 NVFP4、同一个 MTP 文件，各自解码到自己的 EOS（原版的回复更长：monitor 中位 72 个 token，master 52 个；decompose 39 / 24 个）。"加速"相对逐 token 解码的估算（Kv = 1 的主模型前向 graph 耗时 × 解码 token 数；FlashRT 在这条路径上没有用 graph 的逐 token 解码可对照，估算也不含每步的主机开销，所以是下限）。

| 主模型 | 尾部 | monitor × 20：每次前向产出 token / 解码 ms / 加速 | decompose × 2：每次前向产出 token / 解码 ms / 加速 |
|---|---|---|---|
| master | 关 | 2.13 / 623 / 1.74× | 1.52 / 374 / 1.22× |
| master | 默认表 | 2.60 / 511 / 2.12× | 2.61 / 218 / 2.09× |
| master | 整个 prompt | 2.85 / 468 / 2.31× | 2.47 / 230 / 1.98× |
| 原版 | 关 | 2.46 / 726 / 2.00× | 2.30 / 398 / 1.85× |
| 原版 | 默认表 | 2.72 / 656 / 2.21× | 2.92 / 314 / 2.34× |
| 原版 | 整个 prompt | 3.05 / 587 / 2.47× | 3.04 / 302 / 2.43× |

- 草拟头看不到 prompt 是 master 接受率低的主要原因：monitor 每次前向产出的 token 从 2.13 到 2.60（默认表）、2.85（整个 prompt），decompose 从 1.52 到 2.61。
- 草拟头没有跟着 LoRA 训练是次要原因：同样的尾部设置下，原版比 master 高 5–15%（monitor）、12–51%（decompose，只有 2 次调用）；不开尾部时差距最大。两个模型的回复不同，这个对比不是只换草拟头的受控实验。
- 开尾部后 K = 3 在 master 的两类调用上都最快（monitor 511 / 468 ms，decompose 218 ms）：K = 5、7 接受得更多，但每周期更贵；decompose 按长度查表得到的 K = 6 为 241 ms。图像前端的 `generate(spec_k=...)` 可以按调用指定 K；原版模型上 decompose 从 K = 6 的 320 ms 降到 K = 3 的 312 ms，monitor 查表本来就是 3。
- 尾部的 fc 投影（行数 × 10 240 → 5 120）：共用的小 M kernel 在 512 / 2 048 行时要 21 / 84 ms，cuBLASLt 0.24 / 0.97 ms。两者让接受率相差 2% 以内（monitor 每次前向 2.66 / 2.60），按"尾部 + 解码"计 cuBLASLt 更快（decompose 302 → 219 ms）。RTX 前端的尾部 fc 用 cuBLASLt（取启发式的第一个算法）；原版模型上 prefill 从 338 / 258 ms 降到 311 / 172 ms（monitor / decompose），回复不变（`opportunities.md` OPT-039）。
- 主模型一次前向 8k 以内 19.4–19.9 ms、16k 时 22.4 ms，验证 1 个还是 8 个 token 差别很小（4k 时 19.9 / 23.7 ms）；MTP 每草拟一步 0.97 ms。一个周期 = Kv = K + 1 的前向 + K 步草拟，与实测的每周期时间一致。
- 输出不随尾部和 K 变化：master 520 个格子中 516 个与参考一致，不一致的 4 个都是 16 315 token 合成 prompt 在 K = 1 时（`issues.md` ISSUE-109）；原版 520 / 520。合成 prompt 的回复在 12–35 个 token 处就遇到 EOS，接受率的样本太小，只用来看前向耗时随长度的变化。

## 4. 干扰来源拆解

### 4.1 同一进程：主机侧把规划器的等待传给执行器

每个 tick 分三段计时：输入暂存（Python，单独运行 0.5 ms）、graph 发射（5 240 个 kernel 的发射本身要 14 ms 主机时间）、等待完成。

| 实验点（长上下文） | 输入暂存 p50 ms | graph 区间 p50 ms（同 SM 单独：28.0 / 30.9） |
|---|---|---|
| prio | 42.5 | 56.8 |
| green25 | 97.9 | 35.1 |
| green25，切换间隔 0.5 ms | 23.6 | 34.3 |
| green25，读回不占 GIL | 0.5 | 32.4 |
| green25，读回不占 GIL + prefill graph | 0.5 | 33.4 |

- green context 下执行器的 graph 本身只比单独运行慢 10–20%，但输入暂存要等 24–118 ms：执行器线程拿不到 GIL。
- py-spy 只采样持有 GIL 的线程（prio、短上下文）：规划器线程持有 GIL 的样本中 93%（683 个中的 632 个）落在 `qwen36_rtx.py:10077` 的 `fvk.cuda_read_i32_sync`，即每个推测周期把"接受了几个草稿 token"读回 CPU 的那一步。这个绑定在持有 GIL 的情况下执行 `cudaMemcpyAsync` + `cudaStreamSynchronize`，等的是整个验证前向（每周期 20–30 ms）。FlashRT 的 kernel 绑定（`csrc/bindings.cpp` 等）调用期间都不释放 GIL。
- 只把这一次读回改为先在 GIL 之外等待，短上下文的输入暂存回到 0.5 ms，prio 从错过 84.8% 变为 0%。
- 长上下文的第二个来源是分块 prefill：它是 Python 循环逐个发射 kernel（eager）。把解释器线程切换间隔从 5 ms 降到 0.5 ms，这部分等待能减半，但解码为主的短上下文几乎不变（55.9 ms），因为切换间隔只在字节码之间起作用。改用前端已有的 prefill graph 后，green25 长上下文 p99 从 516 ms 降到 35.9 ms。
- 第三个问题是规划器在计时窗口内还会临时捕获 CUDA graph：prio 的窗口内规划器的 graph 从 46–64 个增加到 86–110 个。在 CUDA 默认的全局捕获模式下，另一线程在捕获期间调用 CUDA 会让捕获失败。线程时序一变（py-spy 采样、0.5 ms 切换间隔、读回不占 GIL），就出现 `cudaErrorStreamCaptureUnsupported` 崩溃；改为线程局部捕获模式后不再出现。
- 2B 规划器的旧实验没有这个问题：那里规划器是 HF 的 eager 循环，同进程加 stream 优先级时执行器 p99 只有 35–39 ms（短上下文）。

### 4.2 不限 SM 时：prefill 占满 SM

- prio 去掉主机侧问题之后（读回不占 GIL + prefill graph），长上下文执行器 p99 61 ms，错过率反而从 29.6% 升到 44.2%：prefill 改用 graph 后不再受主机发射速度限制，把 SM 占满，执行器的 graph 在 prefill 期间要 55–60 ms。两进程 mps100 也一样（长上下文错过 33.8%）。
- prefill 计算密集，随 SM 数近似线性变化；解码对 SM 不敏感（第 2 节）。限住规划器的 SM 就能守住截止期（green25 / green50 + 两项修改、mps25、mps50 均为 0–0.1%），代价主要落在 prefill：首 token 慢 2.4–3.3 倍（green25 长上下文 1 877 ms，mps25 2 203 ms），解码每周期慢 1.2–1.7 倍。

### 4.3 SM 隔离之后：显存带宽

| 情形 | 执行器 p50 ms | 相对同 SM 单独运行 |
|---|---|---|
| green25 + 规划器，两项修改（短 / 长） | 35.5 / 34.1 | 1.15× / 1.10× |
| green50 + 规划器，两项修改（短 / 长） | 41.2 / 42.0 | 1.17× / 1.20× |
| mps25 + 规划器（短 / 长） | 37.7 / 35.8 | 1.15× / 1.09× |
| mps50 + 规划器（短 / 长） | 46.1 / 46.1 | 1.20× / 1.20× |
| 48 个 SM 上纯拷贝负载（1.34 TB/s），执行器在其余 122 个 SM | 57.0 | 1.85× |
| 88 个 SM 上纯拷贝负载（1.44 TB/s），执行器在其余 82 个 SM | 106.8 | 3.04× |

- 规划器解码是带宽型负载，SM 隔离之后仍让执行器慢 7–20%；同一块卡上把带宽打满的纯拷贝负载能让执行器慢 1.85–3.0 倍，占的 SM 越多，抢走的带宽越多。
- 在 5090 的 1.5 TB/s 下，这部分干扰还在截止期之内。Jetson AGX Thor 只有约 273 GB/s：此前在 Thor 上，2B 规划器在 SM 隔离后已经让执行器慢 1.8–2.1 倍（`research/experiments/colocation_5090/README.md`），而 27B 解码的带宽需求更大。

### 4.4 功耗与频率

| 情形 | 平均功耗 W | 平均 SM 频率 MHz |
|---|---|---|
| 执行器单独 | 314–321 | 2 841–2 855 |
| mps50（短 / 长） | 565 / 570 | 2 834 / 2 742 |
| mps100（短 / 长） | 552 / 562 | 2 823 / 2 688 |
| prio，读回不占 GIL + prefill graph（长） | 554 | 2 671 |
| prio 长上下文，规划器解码阶段 | 536 | 2 598 |

- 两个模型同时跑时功耗贴近 575 W 上限，SM 频率比单独运行低 1–9%。
- 在 5090 上这是次要因素。Thor 的 CPU 和 GPU 共用约 130 W 的功耗预算，降频的影响要单独测。

### 4.5 显存容量

- 规划器峰值 22.75 GB（prefill 缓冲 2048 行），执行器原始 22.96 GB，两者相加超过 32 GB。执行器必须释放文本编码器和 FP16 源权重（降到 6.30 GB）才能共置。
- 同一进程：分配 28.7–29.0 GB，剩约 2.6–2.9 GB。
- 两个进程：每个进程多一份 CUDA context，执行器进程连同 graph 内存池占 9.6 GiB。
  - 默认规划器下，`process` / `mps100` 启动即 OOM；
  - mps50 / mps25 启动时只剩 0.01–0.14 GB；
  - 规划器 prefill 缓冲降到 1024 行后，剩 1.4–1.5 GB。
- 执行器释放了文本编码器，就不能在线编码新的子任务指令。把规划器输出的新指令交给执行器，需要：
  - 重新放回 Qwen3-4B（约 8 GB）；
  - 用它编码一条新指令，120.7 ms（`research/experiments/colocation_5090/README.md` R3）；
  - 新的文本长度还要重新捕获 graph。

## 5. 痛点

1. **同一进程共置时，主机侧运行时把两个模型耦合在一起。** 两个模型都由 Python 驱动，而 FlashRT 的 kernel 绑定调用期间都不释放 GIL。
   - 规划器的推测循环每周期有一次持有 GIL 的阻塞读回，长上下文 prefill 是 Python 循环逐个发射 kernel，运行中还会临时捕获 graph。
   - 这些在 GPU 侧的机制（stream 优先级、SM 划分）里都看不到，却让执行器错过 80–92% 的截止期。
   - 一处读回改动就能把短上下文的错过率从 84.8% 降到 0%。
2. **prefill 需要 SM，执行器的截止期也需要 SM。** 不限 SM 时，长 prefill 让执行器错过 34–44%。限住规划器的 SM，规划器首 token 就慢 2.4–3.3 倍。静态的 SM 上限按整次调用分配，而 prefill 和解码需要的资源不同：解码本来不缺 SM（28% 的 SM 只慢 16%），却在整个解码期间仍按同样的上限运行。
3. **SM 隔离不隔离显存带宽。** 规划器解码只需要少量 SM 就能跑出它的带宽需求。SM 隔离之后，执行器在 5090 上仍慢 7–20%；带宽打满时可达 1.85–3.0 倍。在带宽只有约 273 GB/s 的 Thor 上，这会是主要干扰。
4. **执行器的空闲窗口装不下规划器的工作单元。** 执行器一次推理 28.7 ms，50 ms 周期只剩约 21 ms 空闲。规划器一个解码周期 24–30 ms，默认一个 prefill 分块（2048 token）约 170 ms。按时间切分（coop）能让执行器几乎不受影响（1.05–1.16×），但要把 prefill 切到 256 token（prefill 慢 43%），规划器一次调用变成 1.8–2.1 倍。
5. **显存容量逼着执行器丢掉文本编码器，规划器到执行器的指令交接没有通路。** 27B 规划器加执行器只能在同一进程或 MPS 下勉强装下，执行器不能常驻 Qwen3-4B（7.6 GB，规划器常驻时只剩 2.6–3.0 GB），换子任务指令时要重新加载，或者另找编码路径；编码器常驻时换一次指令只要 30 ms（新的上下文长度 240 ms）。Thor 是 128 GB 统一内存，编码器可以常驻：执行器连同编码器和 FP16 权重占 23.1 GB，换一次指令 110 ms（新的上下文长度 0.74 s，进程内第一次 11.9 s；`THOR_STATUS_SUMMARY.md` `1104_h` 轮）。
6. **两个模型同时跑会顶到功耗上限。** 5090 上 SM 频率降 1–9%；功耗预算更紧的 Thor 上影响可能更大，目前没有测。

## 6. 可能的解决方向

| 方向 | 针对痛点 | 依据 / 已有工作 |
|---|---|---|
| 运行时去耦：规划器的阻塞读回和同步在 GIL 之外等待（绑定加 `gil_scoped_release`），长上下文 prefill 用 graph，graph 全部预先捕获或使用线程局部捕获；更进一步，执行器走 C++ 运行时（`docs/imagewam_native_cpp.md`），规划器的推测循环在设备上闭环（整次解码一张 graph） | 1 | 本次实验脚本里的两项修改：同进程 green25 长上下文从错过 88.1% 到 0%，规划器 2.29×（两进程 mps25 为 2.58×） |
| 按阶段动态分配 SM：prefill 在执行器空闲窗口内用多 SM，执行器 tick 期间收缩；解码放在少量 SM 上；在 tick 边界切换 green context | 2, 4 | 解码 48 SM 只慢 16%，prefill 需要 SM；Bullet、MuxWise（Drift）、DuetServe、Robion 在 LLM / VLA 上做过动态或按阶段的 SM 划分 |
| 带宽感知的调度与限流：执行器带宽密集段（ActionDiT 10 步的权重流式读取）期间暂停或限速规划器解码，让解码与执行器的计算密集段重叠 | 3 | 纯拷贝负载 1.85–3.0×。Orion 只让资源画像互补的 kernel 共跑。XSched 在 Orin 上把带宽型后台纳入抢占后，前台 P99 从 1.55–1.67× 回到 1.09–1.18×。SGDRC、FGPU 做显存通道划分（只在独显上验证过） |
| 时间切分（coop）+ 可抢占的规划器工作单元：prefill 分块或按层切分到空闲窗口大小，解码周期作为天然让出点 | 4 | coop + 读回不占 GIL：执行器 1.05–1.16×、0% 错过，规划器 1.8–2.1×；对应 Sarathi 式分块 prefill，以及 REEF、GPreempt、Hummingbird 式的 kernel 级抢占 |
| 降低规划器每 token 的字节数：MTP 草拟头看到 prompt 尾部、尾部 fc 投影用 cuBLASLt、按调用指定草拟长度（RTX 上已做），K = 3，针对 master 训练的 MTP 头，更低比特权重，更短的输出格式 | 2, 3 | 每周期 17.5–20.6 GB；接受长度每多 1 个 token，同样的输出少读约 1/3 的权重；monitor 上每次前向产出的 token 从 2.13 到 2.60–2.85，解码 1.74× → 2.12–2.31×；同样尾部设置下原版模型（草拟头与之配套）再高 5–15%（3.5 节） |
| 放宽执行器截止期：动作块异步执行，推理与执行重叠，截止期变为一个动作块的执行时间，而不是一个控制周期 | 4 | 执行器每次推理输出 64 步动作；RTC、VLASH 等异步执行工作 |
| 规划器调用策略：事件触发，按任务阶段降低频率，避开执行器的关键段 | 1–4 | 本次是背靠背调用的最坏情况；规划频率越低，受干扰的时间占比越小 |
| 指令交接：用规划器的隐状态或嵌入作为执行器的条件；缓存有限子任务集合的指令嵌入；把文本编码器量化到 NVFP4 | 5 | R3：在线编码 120.7 ms，约 8 GB；缓存命中的 `set_prompt` 只要 0.05 ms |
| 功耗感知：共置时联合分配功耗与频率（DVFS） | 6 | LithOS 的透明 DVFS；边缘隔离实测中，Orin Nano 两模型并行时频率降到约一半 |

## 7. 可优化的目标与指标

**主目标：规划决策的生效延迟，约束是执行器不超过截止期。** 生效延迟是从一次规划调用到期（harness 的检查时刻），到执行器按这次调用的结果行动为止经过的时间，以控制步计（15 Hz，一步 66.7 ms）；约束是执行器每个动作块都在 533 ms 内给出（3.1–3.3 节的背靠背设定为每 tick 50 ms），错过率 ≤ ε。选它的原因：

1. 它是 harness 实际在等的量。同步协议下它就是机器人的停顿：每个 episode 规划器 14.5 / 16.4 s，占仿真时间的 27–31%；并发时它是决策滞后：prio 下 monitor 的 p50 为 18 / 21 步（腕部 224 / 1280×720），进程里第一次调用 52–69 步（3.4 节）。
2. 它包含双模型系统才有的一段：规划器换了子任务，执行器要换指令。文本编码器常驻时换一次 30 ms（新的上下文长度 240 ms），Thor 上 110 ms（0.74 s）；5090 上规划器常驻时编码器装不下，这一段目前没有通路（第 5 章痛点 5）。单模型推理服务的指标覆盖不到这一段。
3. 它能对应到任务结果：决策晚到时，机器人会在已经完成的子任务上继续动作，失败恢复也会推迟；同步协议下的停顿直接拉长完成时间。
4. 它能拆成可以单独测量的分量，每个分量都有对应的手段：

| 分量 | 本次取值（5090，monitor） | 对应方向（第 6 章） |
|---|---|---|
| ViT + prefill | 0.40 / 0.60 s（腕部 224 / 1280×720） | prefill 提速；按阶段分配 SM |
| 解码 | 草拟头没有 prompt 尾部时 0.62 s，补上后 0.47–0.51 s（3.5 节，K = 3）；没有 EOS 停止、按 `max_tokens` 512 解码时整次调用 11 s | EOS 停止；MTP（prompt 尾部、K = 3、配套的草拟头） |
| 运行中的 graph 捕获 | 冷调用多约 0.2 s；进程里第一次 monitor 3.3–3.8 s | 按长度区间预先捕获 |
| 指令交接 | 编码器常驻 30–240 ms；5090 共置时没有通路 | 指令嵌入缓存、编码器量化、用规划器的隐状态作为条件 |
| 共置干扰 | prio 下 monitor 慢 1–3%，green50 慢 28–31% | 运行时去耦、SM 与带宽的隔离和调度 |

执行器错过率 ≤ ε 约束下的规划器调用延迟仍是更紧设定下的目标：执行器每个控制步都要给出动作、规划器背靠背调用（3.1–3.3 节，零错过要规划器慢 1.36–2.58 倍），或者在 Thor 上（`1104_h`：green25 和 mps100 各有 3 次超过 533 ms；2B 的替身单次调用 6.6–7.8 s，已经超过 5.33 s 的检查间隔）。在 harness 的调用频率下，5090 上这个约束不起作用：prio 下超过一个控制步的查询占 0–0.7%，没有一次超过一个动作块。多个"规划器 + 执行器"组合（多个任务或多台机器人）共用一块卡时，还要加一个吞吐目标：截止期约束下一块卡能同时服务的组合数，本次没有测。

候选指标按层面列在下表，层面的划分依据如下：

- 执行器实时性和规划器响应分开：两个模型各有一个由控制回路决定的时间要求。执行器要在当前动作块执行完之前给出下一块；规划器要在下一次检查到期之前返回。
- 联合目标写成"约束 + 目标"，不写成加权和。执行器错过截止期时机器人没有动作可执行，是有门槛的；规划器是尽力而为，在检查间隔内返回就有用；两者单位不同，加权系数无从确定。有限次测量只能给出 p99 和最大值，所以约束写成 ≤ ε，而不是 = 0。
- 主机侧单列一层：效果最大的一次改动在主机侧（改一处读回，错过率 84.8% → 0%），而 SM 占用、p99 这类 GPU 侧指标看不出这个机制。
- 资源层面是装不装得下、会不会降频的硬约束：执行器的文本编码器放不下，功耗顶到上限时 SM 降频 1–9%；在 Thor 上这两项更紧。
- 任务层面是系统指标最终要换算成的结果：成功率和完成时间。
- 尾部用 p99 和最大值，因为错过截止期是尾部事件；减速相对同样 SM 数的单独运行计算，把"划走一部分 SM"本身的代价和另一个模型的干扰分开；首 token 时间和每解码周期分开记，因为 prefill 受 SM 限制、解码受带宽限制。

| 层面 | 指标 | 本次取值范围 |
|---|---|---|
| 执行器实时性 | 控制周期内的错过率；p99 / 最大响应延迟；实际控制频率；相对同 SM 单独运行的减速 | 0–100%；32–759 ms；0.8–20 Hz；1.05–5.24× |
| 规划器响应 | 首 token 时间（ViT + prefill）；一次调用延迟；每解码周期时间 / token 每秒；每次主模型前向产出的 token 数；单位时间内的规划次数 | prefill 54–2 203 ms；调用 0.67–3.44 s；每周期 23.8–58.8 ms；每次前向 1.52–3.05 个 token |
| 联合目标 | 生效延迟（截止期约束下）；执行器错过率 ≤ ε 约束下的规划器吞吐（或调用延迟）；执行器 p99 与规划器调用延迟的 Pareto 前沿；零错过所需的规划器代价 | 生效延迟 p50 18–27 步，最大 52–69 步；错过率 ≤ 0.1% 的配置下规划器代价：短上下文 1.36–2.10×，长上下文 1.55–2.58× |
| 主机侧 | 执行器每 tick 在主机侧的等待（输入暂存、发射）；规划器持有 GIL 的时间占比；运行中的 graph 捕获次数 | 输入暂存 0.5–118 ms；读回占规划器持 GIL 时间的 93%；冷 monitor 中位 5–6 个，第一次 56–59 个 |
| 资源 | 显存余量与能否装下；平均功耗与 SM 频率；每次执行器推理 / 每个规划 token 的能耗；带宽份额 | 余量 0.01–2.9 GB；314–570 W；2 598–2 872 MHz |
| 任务层面 | 执行器换指令的时间；带真实延迟注入的闭环成功率与完成时间；对环境变化的反应时间 | 换指令 30–240 ms（5090，编码器常驻），110–745 ms（Thor）；闭环指标本次未测 |

## 8. 局限与下一步

- 27B 规划器的共置只在 RTX 5090 上测过。27B 在 Thor 上单独跑过一轮（`1104_h3`，图像前端 `Qwen36VlTorchFrontendThor`：语言模型 `Qwen36TorchFrontendThor`，ViT 用 BF16 线性层和 SDPA）：22 次录制调用中，monitor 一次 6.97–7.02 s（中位；ViT 0.27、prefill 4.36、解码 2.31–2.35 s），20 次全部超过 5.33 s 的检查间隔，是 5090 的 6.7 倍；prefill 占 62%（5090 为 30%），是 5090 的 13.8 倍，解码是 3.6 倍。MTP 尾部 fc 在 Thor 上推算每行约 0.77 ms（decompose 的 2 048 行约 1.6 s），单独计时与改用 cuBLASLt 在下一轮。回复与 5090 参考全部不同；在 5090 上只换成同样的 ViT 配置，22 次调用中有 4 次决策改变（issues.md ISSUE-112）。Thor 上用 Qwen3-VL-2B 替身按 harness 节奏（执行器 533 ms 一个动作块，规划器每 5.33 s 一次，约 4k token）测过一轮（`1104_h`）：prio 和 mps50 没有查询超过 533 ms，green25 和 mps100 各有 3 次 543–571 ms，都落在规划器 prefill 内；替身的单次调用 6.6–7.8 s，已经超过 monitor 的间隔。
- 3.1–3.3 节的规划器是背靠背调用的最坏情况，执行器是 fp8、10 步、50 ms 周期；3.4 节按 harness 的调用频率回放（monitor 每 80 步，执行器每 533 ms），但调用内容是录制后回放的，规划器的回复不会改变 harness 的控制流。
- 没有闭环任务指标。仿真里推理期间时间是静止的，需要带延迟注入的闭环，才能把延迟换算成成功率。
- 共置时的数值一致性未查清：两个模型不分 SM 共享时（`prio`、`coop`），规划器约 60 次调用里有 1–2 次输出不同，都发生在运行中临时捕获 graph 的那次调用；执行器约 0.5% 的 tick 动作有最大 4.9e-3 的差异；分 SM 的配置里都没有出现（`issues.md` ISSUE-105、ISSUE-106）。
- 执行器的基线依赖 cuBLAS 版本：本次所有对比都在 cuBLAS 13.4.1.3 下进行，执行器单独运行 28.2–28.8 ms；环境原本的 13.6.1.10 下为 24.2 ms，差距全在 fp8 GEMM 上（17.5 → 13.4 ms），与内核库的构建无关（ISSUE-103）。共置结果尚未在 13.6.1.10 下重测。在非默认 stream 上构造规划器前端得到错误输出的问题已修复（ISSUE-104）。
