# Jetson Thor 上的规划器 + 执行器：问题、证据与工作项

本文件把长程规划–执行场景在 Jetson AGX Thor 上的工作串成一条链：目标指标 → 已测得的现状 → 三类 Thor 特有问题各自的证据与判断 →
每个工作项的目的、做法、预期与意义。数字都注明出处（`THOR_STATUS_SUMMARY.md` 的轮次、各实验目录的 README）；
推算与假设单独标出。执行状态见 `plan.md` 的 "Plan: Thor monitor-call latency, decision quality and co-location"。

## 1. 目标指标

**从调用开始到决策可用（L）**：harness 发起一次规划器调用（当前画面已拍下）到回复里 `action` 的值完整解码、可以解析
（它的右引号已生成）的墙钟时间。包含预处理（聊天模板、图像）、ViT、图像特征注入、前缀 capsule 恢复（复用时）、prefill、
解码到 `action` 闭合；不包含其后的 `reason` 文本与执行器切换指令的时间。

- 解码到 EOS 的做法里，harness 在回复结束后才解析 JSON，L 等于整次调用时间；"action 闭合即停"时 L 短于整次调用。
- 同步协议下机器人在 L 期间不动：等待占比 = L /（L + 检查间隔内的控制时间）。VoLoAgent 的 harness 每 80 个控制步（15 Hz）
  检查一次，控制时间 Δ = 5.33 s。
- 异步协议下 L > Δ 意味着下一次检查到期时上一次决策还没出来，调用堆积，且决策依据的画面已是 L 之前的。

三项约束，各对应一个受影响的对象：

| 约束 | 受影响的对象 | 量 |
|---|---|---|
| L < Δ，且越小越好 | 机器人（等待） | L 的中位与最大值；等待占比 |
| 执行器不错过控制截止期 | 执行器 | 执行器调用的 p99；超过截止期的比例 |
| 决策与原始路径一致 | 任务质量 | 干预决策（`replan`、`next`、工具动作）与参考的一致数 |

## 2. 现状（Jetson Thor，官方 Qwen3.8-27B NVFP4，monitor 调用，腕部 224）

| 路径 | L | 等待占比（推算） | 出处 |
|---|---|---|---|
| 原始：每次全部 prefill，解码到 EOS | 6.40 s | 55 % | `1110_h7h4bh8` H8 |
| 复用固定前缀 + action 闭合即停 | 2.61 s | 33 % | `1110_h7h4bh8` H8（20 次） |
| 同上，闭环干预回合 | 2.68 s（最大 2.85 s） | 33 % | `1111_h12h11h9` H11（27 次，含 3 次 `next`） |
| 同上 + prefill 线性注意力换 `wy_lt` | 1.77 s（最大 3.47 s） | 25 % | `1111_h14h13` H13（47 次；3 次参考决策与 `native` 不同） |
| RTX 5090 同一提示词，原始 / 快路径 | 1.06 / 0.34 s | – | `experiments/monitor_call/README.md` |

- 5090 上原始路径已远低于 Δ；Thor 上原始路径高于 Δ（`1104_h3c` 回放 40 / 40 次超过）。L 超过间隔只在 Thor 上发生。
- 快路径的 2.6–2.7 s 里：prefill 约 2.0 s（75–77 %），解码约 0.43–0.51 s，ViT 与预处理约 0.15 s。
- Thor 相对 5090：prefill 13.8 倍，解码 3.6 倍（`1104_h3c`）。瓶颈从 5090 上的解码移到了 Thor 上的 prefill。
- Thor 的 prefill 有 55 % 在一个线性注意力 kernel 上：Thor 前端对每个 prefill 分块走逐步递归的 `native` 路径，
  这一个 kernel 2 235 ms，是 5090 WY 路径 69 ms 的 32 倍，同一次 prefill 里 fp4 GEMM 只是 3.8 倍（`1110_h7h4bh8` H4b）。
  5090 的 WY 分块（`wy_lt`）在 Thor 上逐层与 5090 相同、不漂移，整段 prefill 3 994 → 2 294 ms（`1111_h12h11h9` H9，
  `experiments/gdn_wy_thor/README.md`）。
- 决策：快路径在 47 次调用上 action 全部不变，含 3 次 `next`（H8 20 次、H11 27 次）。官方模型在闭环回合里只复现了 master 6 次
  `next` 中的 3 次，另外 3 次给 `continue`；这是模型之间的差，与快路径无关。
- 换 `wy_lt` 之后（H13）：同一运行内快路径与该运行自己的 `generate` 47 / 47 决策相同；与 `native` 运行比，参考决策变了 3 次
  （t0e1 第 240 步 `next` → `continue`、t0e1 第 480 步 `continue` → `replan`、t8e1 第 240 步 `continue` → `next`）。`native` 与 5090
  在同 47 次上也差 3 次；与录制的 master 决策一致数 `wy_lt` 43、`native` 44、5090 43。MTP 每次尝试接受 1.77（`native` 1.83）。
- Thor 上同一提示词连续生成 5 次，第 2–5 次与第 1 次只有 44 / 80 相同（5090 为 80 / 80），差异都在 `reason` 文本或开头的
  ```` ```json ```` 围栏，100 次决策全部相同（`1111_h12h11h9` H12，GPU 上另有进程）。每次重复之前先生成上一个调用、GPU 空闲时
  79 / 80 相同（`1111_h14h13` H14，issues.md ISSUE-114）。

## 3. 三类 Thor 特有问题

延迟是结果；带宽与热态是 Thor 上影响延迟和执行器的两个机制。

### 3.1 延迟：真问题，主线

- 为什么 Thor 特有：只有 Thor 上 L 超过 Δ。
- 证据：第 2 节。快路径已把 L 压到 Δ 以下，但同步协议下仍有约三分之一的时间在等；剩余部分以 prefill 为主，
  而 prefill 最慢的一段是 Thor 前端选的逐步递归路径；5090 的分块路径在 Thor 上数值同样正确、快 43 %。
- 判断：把 Thor 的 prefill 线性注意力换成 `wy_lt` 是收益最大的一步，且不需要写 kernel：实测 L 2.61 → 1.77 s，MTP 接受率
  低 3 %。代价是 47 次里 3 次接近平局的调用决策与 Thor 原来的路径不同，幅度与两台机器之间的差相同。是否切为 Thor 默认取决于
  "决策与原始路径一致"按哪条路径算（plan.md Phase 8）。解码在闭合即停之后只剩约 0.43 s，不再是瓶颈。

### 3.2 带宽：真问题，需要共置实测

- 为什么 Thor 特有：两个模型共用一份统一内存（拷贝约 236–256 GB/s），按 SM 分区隔不开带宽。
- 证据（Thor）：8 个 SM 就能把拷贝带宽用满；SM 不相交时纯拷贝负载仍让执行器慢 1.80 倍（`1029`）；执行器变慢集中在与规划器
  解码重叠的调用上，为单独运行的 1.3–1.7 倍，与 prefill 重叠几乎不慢（`1030`）；green 分区下执行器 p99 高 21–41 %（`1028`）；
  规划器解码稳态约 200 GB/s，为拷贝上限的 85 %（`1104_h3c`）。
- 缺口：上述测量用的是替身规划器或纯拷贝负载；真实 27B 规划器与执行器按 harness 节奏共置尚未在 Thor 上测。

### 3.3 热态：在共置部署下大概率不是主要问题

- 现象：同一进程空闲一段时间后，规划器解码每周期 142 ms（稳态 87.2 ms，1.63 倍），持续 35–60 s；拷贝带宽低约 6 %，
  prefill 几乎不变；GPC、NVD 与 CPU 频率不变（`1111_h10`，issues.md ISSUE-112）。
- 阈值：空闲 5–120 s 0 / 5 次出现（`1110_h7h4bh8` H7），180 s 1 / 2 次，300 s 2 / 2 次（`1111_h10` 无干扰的段）。
  平台值每次相同，像是一个离散的低功耗状态。
- 部署里的影响（推算）：harness 的调用间隔只有几秒，进入不了这个状态；只有任务之间空闲 3–5 分钟以上时，之后约一分钟内的调用
  解码变慢，快路径的约 0.45 s 解码变成约 0.73 s，L 多约 0.3 s。
- 假设：与执行器共置时，执行器的周期负载让内存系统保持在快状态。`1111_h10` 前两段有另一个进程在跑、没有形成完整平台，
  与这一假设一致，但那个进程的负载没有记录，不算验证。
- 判断：热态的 Thor 侧问题已经量清楚；共置时的热态并入带宽那一项一起看。

## 4. 工作项

### W1（H9 → H13）：让 Thor 的 prefill 线性注意力走分块路径（已测，默认待定）

- 目的：压缩快路径 L 里占 75 % 的 prefill。
- 已完成（H9）：同一份层输入上比较七个变体与逐 token 路径。`wy_lt` 在 Thor 上逐层与 5090 相同（cos 中位 0.999765），
  只有手写 mma 的 `wy` 在 SM110 上出错；Thor 上 `wy_lt` 的 prefill 2 294 ms，现路径 3 994 ms。
- 改动：`FLASHRT_QWEN36_THOR_LIN_PREFILL=parent` 加 `FLASHRT_QWEN36_TQ_PREFILL_GDN_BACKEND=wy_lt`，让 Thor 前端的 prefill
  线性注意力层走父类的分块分支（默认不变）。
- 结果（H13，47 次调用，GPU 空闲）：prefill 2 026 → 1 181 ms（对齐复用），L 中位 2 613 → 1 768 ms（同 47 次），等待占比
  33 % → 25 %；最大 3 465 ms 是一次以文字开头、第 69 个 token 才闭合 `action` 的回复。MTP 每次尝试接受 1.83 → 1.77，
  解码每 token 30.3 → 31.5 ms。决策：同一运行内快路径 47 / 47 与 `generate` 相同；参考决策与 `native` 运行差 3 次（见第 2 节），
  在该运行的每一格里一致，不是运行间差异。完整复用（截在第一张 NOW 图）在 `wy_lt` 下改回复 47 / 47、决策 3 次，与 5090 相同。
- 待定：Thor 默认是否切到 `wy_lt`。`native` 与 `wy_lt` 都不是决策的真值：两者与 5090 各差 3 次，与录制的 master 决策一致数
  44 与 43。plan.md Phase 8 等决策判据。
- 意义：Thor 的慢不在算力，而在前端为 Thor 选的递归路径；换路径对 decompose 与 720 腕部图的长提示词（5.7k token）同样有效。

### W2（H11）：在含干预决策的调用上检验快路径（已完成）

- 结果：闭环里含 `next` 或失败的 6 个回合、27 次调用，对齐复用 + 闭合即停 27 / 27 决策不变，含 3 / 3 次 `next`；
  L 中位 2.68 s、最大 2.85 s。
- 意义：5090 上的教训是近似手段让 `continue` 不变、却翻转了全部 3 次干预决策（`experiments/monitor_call/README.md` Finding 4）；
  对齐复用在 Thor 上没有这种变化。样本里的干预只有 `next`，没有 `replan` 与工具动作。

### W3（H12 → H14 → H15）：Thor 上运行间差异的大小与来源

- 结果（H12）：第 2–5 次与第 1 次 44 / 80 相同，差异都在 `reason` 文本或围栏，决策 100 / 100 相同。7 次调用里第 2–5 次在同一位置
  偏离第 1 次，第 1 次紧跟在上一次调用之后，第 2–5 次紧跟在同一提示词之后。
- 假设：上一次调用留下的某块状态被下一次调用读到（ISSUE-114）。
- 结果（H14）：每次重复之前先生成一次上一个调用，GPU 空闲：79 / 80 相同，19 / 20 次调用 5 次全同，支持留存状态。
  H12 与 H14 之间 GPU 是否另有进程也变了；H12 第 2–5 次中间的单次不同用留存状态解释不了。
- 下一步（H15）：H12 的顺序在 GPU 空闲时重跑，把顺序与另一个进程的作用分开。后者就是共置条件：执行器经 MPS 共用 GPU 时，
  规划器回复是否因此变化。
- 意义：Thor 上所有"回复是否相同"的比较都以它为噪声底；若是留存状态，它是 Thor 前端的一个缺陷，修掉后回复比较才有意义。

### W4：规划器进程，供 Thor 上的共置测量使用

- 目的：用真实 27B 规划器与快路径做共置测量。
- 做法：独立进程载入 Thor 图像前端，按 harness 节奏（每 5.33 s 一次 monitor）回放录制调用，原始与快路径两组，
  每次调用记录开始、决策可用、结束三个时间戳；运行前取得 Thor 上共用的 GPU 独占锁。执行器与共享方式由共置测量一方提供。
- 预期（假设）：执行器变慢集中在与规划器解码重叠的时段，快路径把每次 monitor 的解码从约 2.1 s 缩到约 0.45 s，
  执行器 p99 与超过截止期的比例应随之下降；规划器在共置下的 L 由测量给出。
- 意义：若成立，同一改动同时缓解延迟与带宽争用，把 3.1 与 3.2 用一个机制连起来。

### W5（H10）：热态的 300 s 问题（已完成）

- 结果：见 3.3 节。阈值在 120–300 s 之间，平台 1.63 倍、持续 35–60 s。

## 6. 不在当前工作项里的方向

| 方向 | 理由 |
|---|---|
| 继续优化解码（MTP、K） | 闭合即停之后解码约 0.45 s，不是瓶颈 |
| 修手写 mma 的 `wy` kernel | `wy_lt` 已在 Thor 上正确且更快 |
| 更多视觉复用 | 固定前缀（系统提示 + BEFORE 图）已全部复用；NOW 图每次不同 |
| RTX 5090 上的进一步优化 | 5090 上 L 已远低于 Δ |
| Thor 上的仿真闭环 | 当前执行器几乎不读指令（`experiments/sim_closed_loop/README.md` Finding 1），闭环体现不出分层的收益；价值在演示与 Thor 上的实际等待占比，先只做可行性检查（MuJoCo / robosuite 能否装进用户级环境） |
