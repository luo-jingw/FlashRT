为什么用 VoLoAgent 的调用

  1. 有对照证据的分层系统：同一 π0.5 加上它的编排，成功率 12.57 → 41.80 %（Q1b 卡片）。
  2. 开源代码把循环定义完整：三类调用、调用时刻、提示词、输出格式与 max_tokens 都可读出，可以录制成可重放的调用。多数论文不报告这些参数。
  3. monitor 是多图长上下文（4.1–5.7k token），高于已报告的所有规划器上下文，正是 Thor 上 prefill 成为瓶颈的情形；RoboCerebra 是短上下文、长任务的一端，两者互补。
  4. 只取它的调用结构与节奏，规划器模型可替换：Thor 上用官方 Qwen3.8-27B。

Q3b延迟怎么降

去掉规划器调用里的冗余计算，分三步。Thor 上 L 6.92 → 1.78 s，低于 Δ，等待占比 56 % → 25 %；同一配置下决策不变。J
1
复用固定前缀

为什么能做：同一回合的每次 monitor，系统提示与 3 张回合开始时的图逐 token 相同，占输入的 61–65 %。回合开始时把这段算完的模型状态存起来，之后每次恢复，只编码 3 张当前图、只 prefill 剩下的 token。

2
action 闭合即停

为什么能做：回复里的决策在第 9–16 个 token 就完整，其余约 80 % 是 reason 解释；harness 按 action 行动。1 + 2 合称两项优化，先在 RTX 5090 上验证：1 057 → 338 ms，回复与决策逐 token 相同。

3
prefill 换成分块路径 wy_lt

为什么能做：1、2 之后剩下的以 prefill 为主；prefill 的 55 % 在一个逐 token 递归的线性注意力 kernel 上（H4b）。5090 用的分块路径 wy_lt 在 Thor 上同样准确（H9），只是 Thor 前端没有用它。

native、wy、wy_lt 是什么串行 4 093 步 → 64 块矩阵乘法同一个计算的三种做法

Qwen3.6 / 3.8 的 64 层里 48 层是线性注意力（Gated DeltaNet）。每层有一个状态矩阵，每读入一个 token 就按"门控 delta 规则"更新一次：先衰减，再擦掉这个 token 的 key 方向上的旧内容，再写入新的 value。prefill 要让提示词的几千个 token 依次更新它。

native：逐 token 递归

每个 token 的更新依赖上一个 token 的结果，4 093 个 token 就是 4 093 个必须依次完成的小步，每一步的计算量很小，GPU 大部分算力闲着。

WY 分块：每 64 个 token 一块

一块内 64 次连续更新可以合并写成"单位矩阵减去两个矩阵的乘积"（WY 表示，源自 Householder 变换的乘积），于是一块的作用变成几次矩阵乘法，用 tensor core 完成；串行的只剩块与块之间的 64 步。

同步协议

检查到期时机器人停下，规划器回复完再继续执行。规划器的延迟直接变成机器人的停机时间。VoLoAgent 与 RoboCerebra 的开源代码都是这种协议。

异步协议

规划器在后台运行，机器人继续执行当前子目标；决策晚 L 才到，这段时间按旧指令或旧观测动作。L 超过检查间隔时调用堆积。

harness

把规划器、执行器与环境串起来的控制循环：什么时候调用规划器、每次给它什么输入、它的输出怎么变成执行器的指令。

LLM 服务的延迟考核

数据中心的 LLM 服务用 SLO（服务等级目标）考核延迟，常用两个量：TTFT（time to first token，从请求到第一个输出 token 的时间）和 TPOT（time per output token，之后每个 token 的时间），看大量请求上的 p50 / p99。单个请求慢一点只影响统计分布，不会让某台机器停住。

两项优化（RTX 5090 上先验证）

  1. 复用固定前缀：回合开始时把系统提示与 3 张回合开始时的图算完后的模型状态存起来，之后每次调用恢复它，只编码 3 张当前图、只 prefill 剩下的 token。前缀截在 2 048 token 的整数倍上，结果与整段 prefill 逐 token 相同。
  2. action 闭合即停：action 的值一闭合就停止解码，不生成 reason。
