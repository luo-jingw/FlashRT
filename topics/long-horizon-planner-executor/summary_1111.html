Q1c这样的系统怎么运行，规划器延迟意味着什么

规划器每隔一个检查间隔 Δ 看一次进度，执行器高频输出动作。规划器的延迟 L 进入机器人的关键路径：同步协议下机器人停着等，代价是时间；异步协议下机器人按旧指令执行，代价是质量。规划器延迟超过检查间隔时会怎样，文献里没有测量。

同步：14.7 s 里机器人只动了 10.7 s。停着的时间占比 = L / (L + Δ)，称等待占比；文献常用的执行占比（motion duty cycle）就是 1 − 等待占比。代价是时间。

异步：机器人一直在动，但每次检查后的 L 秒里按旧指令或旧观测动作（斜纹）；L 超过 Δ 时调用堆积。代价是质量。

Q2b用什么量衡量 challenge 的影响

每个 challenge 都用同样三个量说明它的影响。M1 就是 Q1c 的 L 与等待占比；M2、M3 是另外两个对象：执行器与任务决策。Q3a 给这三个量定目标。
M1 · 机器人L 与等待占比

L = 从调用开始到决策可用（定义）；等待占比 = L / (L + Δ)。L 超过 Δ 时调用开始排队。

M2 · 执行器截止期错过率

执行器没能在旧动作块用完前给出新动作块的比例；看 p99 与错过率（严格 200 ms，宽松 600 ms）。

M3 · 任务决策决策一致数

同一次调用，加速或换条件后，continue / next / replan 与原始路径相同的次数。

Q2cchallenge 排序与主线划分

按影响排序：影响 = 在 M1 / M2 / M3 上的实测幅度 × 出现的频繁程度。第 1 项是规划器延迟，第 2、3 项是它在 Thor 上的两个原因，构成 Jingwu 的主线；第 4、6、7 项发生在两个模型之间，由 Chenwei 的共置测量负责。点开每项看现象、证据、本周对应的实验，以及数据中心 LLM 服务为什么没有这个问题。

Thor 上 prefill 为什么慢 12–14 倍，decode 只慢 3.6 倍

理论：prefill 一次处理几千个 token，每读一遍权重要做几千次乘加，是计算密集的，速度取决于算力；decode 每次只算一个（或几个，MTP）token，读一遍权重只做很少的计算，是访存密集的，速度取决于内存带宽。所以两个阶段的差距分别跟着算力之比和带宽之比走。

实测拆开看（H4b、H9）：

  • 线性注意力慢 32 倍，远超算力之比：Thor 前端用逐 token 的 native，算法本身是串行的，用不上算力（A4）。它占 Thor prefill 的 55 %。
  • fp4 GEMM 慢 3.8 倍，低于算力之比：5090 在这个形状上大概没跑满峰值（推断）。
  • 换成 wy_lt 后，算法相同，prefill 差距剩 7.1 倍，落在算力之比与带宽之比之间。
  • decode 慢 3.6 倍，低于带宽之比 6.6 倍：5090 的 decode 也没跑满带宽（推断）。

结论：12–14 倍 = 算法（逐 token，可修）× 硬件（算力少，修不了）。前者就是 Q3b 第 3 步做的；修完之后剩下的约 7 倍是硬件差距，只能靠少算（第 1、2 步）来抵消。

为什么仍研究两模型系统

  1. 任务需要开放词汇理解、世界知识或长记忆时，强的独立规划器有明确收益（VoLo、Gemini Robotics 1.5）。
  2. 两层运行频率不同：规划器约 1 Hz 或更低，执行器每秒十几到几十次。
  3. 两层可单独替换，复用预训练 VLM 的推理能力，不必在窄的控制数据上重新训练。
  4. 现有的 agent 系统（VoLoAgent、Gemini Robotics、Hi Robot、RoboCerebra 的评测循环）多是这种结构。

VoLoAgent（W-VOLO）

智能体式的规划–执行系统（arXiv 2606.07723），开源 harness：开局 decompose，每 80 个控制步 monitor，事件触发 replan；执行器 π0.5。

为什么用它的调用：

  1. 有对照证据：同一 π0.5 加上它的编排，成功率 12.57 → 41.80 %。
  2. 开源代码把循环定义完整（调用时刻、提示词、输出格式、max_tokens），可以录制成可重放的调用；多数论文不报告这些参数。
  3. monitor 是多图长上下文（4.1–5.7k token），正是 Thor 上 prefill 成为瓶颈的情形；与 RoboCerebra 的短上下文互补。
  4. 只取调用结构与节奏，规划器可替换：Thor 上用官方 Qwen3.8-27B。

RoboCerebra（W-RC，Chenwei）

长时程操作基准（arXiv 2506.06677，NeurIPS 2025），平均 9.1 个子步、2 972 个仿真步；自带规划器 + VLA 的评测循环：开局 decomposition（编号列表）、周期 monitor、子目标边界 switch。Chenwei 的回放用 2B / 7B 规划器，monitor 约 470 token，执行器每 600 ms 释放一次。

"1–2 个子目标"

每个回合开始时，规划器的 decompose 调用把任务指令拆成子目标列表，执行器逐个执行。W-VOLO 的 6 段录制里，ep0 / ep43 拆成 1 个（如 "turn on the stove and put the moka pot on it"），ep188 拆成 2 个（"put the alphabet soup … in the basket"、"put the tomato sauce … in the basket"）。

原始路径

Thor 上不加任何加速的做法：同一个模型（官方 Qwen3.8-27B NVFP4）、同一台机器、同一个提示词，整段 prefill（不复用前缀），线性注意力用 Thor 前端默认的 native，贪心解码到 EOS，解析完整 JSON 里的 action。

"决策一致"= 加速路径对同一次调用给出的 action 与它相同。因为 Thor 上同一路径重复运行也偶尔翻转（A5），比较在同一次运行内做。

查过、目前不是问题

  1. CPU 发射开销：prefill 中 kernel 以外的时间占 0.9 %，eager 与 CUDA graph 的 prefill 一样快（3 984 / 3 977 ms）。
  2. 内存容量：27B NVFP4、前缀状态（176–195 MB）与执行器都放得下。

Jingwu 与 Chenwei 已商定的接口

  1. 统一的 FlashRT commit，报告写明 CUDA / cuBLAS / 驱动 / L4T 版本与功耗模式。
  2. L 拆成 L_decision（到决策可用）与 L_reply（到回复结束）。
  3. Jingwu 交付规划器进程（原始 / 快路径两组，每次调用记开始、决策可用、结束）；H16 是它的单独运行基准。
  4. Thor 上共用一把 GPU 独占锁。

图像复用的负面结果（Chenwei）

RoboCerebra 负载下，848 次调用里只有 3 次与上一次共享图像，图像复用几乎省不了时间。VoLoAgent 负载下，monitor 输入的 61–65 % 在回合内不变，复用整个前缀能省一半 prefill。结论取决于负载。

L：从调用开始到决策可用

harness 发起调用（当前画面已拍下）到回复里 action 的值完整生成、可以解析的时刻。包括图像预处理、ViT、prefill、decode 到 action 闭合；不包括其后的 reason。

Δ = 5.33 s：检查间隔

VoLoAgent 每 80 个控制步调用一次 monitor，控制频率 15 Hz：80 / 15 = 5.33 s。取自已有的 agent / harness 配置。

同步协议

检查到期时机器人停下，规划器回复完再继续执行。规划器的延迟直接变成机器人的停机时间。VoLoAgent 与 RoboCerebra 的开源代码都是这种协议。

异步协议

规划器在后台运行，机器人继续执行当前子目标；决策晚 L 才到，这段时间按旧指令或旧观测动作。L 超过检查间隔时调用堆积。

harness

把规划器、执行器与环境串起来的控制循环：什么时候调用规划器、每次给它什么输入、它的输出怎么变成执行器的指令。

LLM 服务的延迟考核

数据中心的 LLM 服务用 SLO（服务等级目标）考核延迟，常用两个量：TTFT（time to first token，从请求到第一个输出 token 的时间）和 TPOT（time per output token，之后每个 token 的时间），看大量请求上的 p50 / p99。单个请求慢一点只影响统计分布，不会让某台机器停住。

两项优化（RTX 5090 上先验证）

  1. 复用固定前缀：回合开始时把系统提示与 3 张回合开始时的图算完后的模型状态存起来，之后每次调用恢复它，只编码 3 张当前图、只 prefill 剩下的 token。前缀截在 2 048 token 的整数倍上，结果与整段 prefill 逐 token 相同。
  2. action 闭合即停：action 的值一闭合就停止 decode，不生成 reason。

5090（官方模型，腕部 224）：1 057 → 338 ms，回复与决策逐 token 相同。由 Jingwu 实现。

native：逐 token 的线性注意力 prefill

Qwen3.8-27B 的 64 层里有 48 层是线性注意力，每层有一个随 token 逐个更新的状态矩阵。native 让 token 一个接一个地更新它：4 093 个 token 就是 4 093 个必须依次完成的小步，GPU 大部分算力闲着。

谁写的：上游 FlashRT 项目（flashrt-project/FlashRT）；它的 Thor 前端一律用这条路径（PR #57）。不是 Jingwu 写的。

wy：WY 分块，手写 kernel

把每 64 个 token 的连续更新合并写成矩阵乘法（WY 表示），串行步数从 4 093 降到 64。wy 的矩阵乘法用手写的 tensor core kernel 实现。

谁写的：上游 FlashRT 项目（PR #53），算法照 FLA（flash-linear-attention）库移植。在 Thor（SM110）上结果错误，原因未查。不是 Jingwu 写的。

wy_lt：WY 分块，cuBLASLt

与 wy 数学完全相同，矩阵乘法交给 NVIDIA 的 cuBLASLt 库；RTX 5090 的默认路径。在 Thor 上与 5090 同样准确，prefill 3 994 → 2 294 ms。

谁写的：上游 FlashRT 项目（PR #53）。Jingwu 加了开关 FLASHRT_QWEN36_THOR_LIN_PREFILL=parent 让 Thor 前端可以走它；Thor 默认仍是 native。
