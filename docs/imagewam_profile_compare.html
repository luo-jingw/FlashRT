跨表结论

  1. ActionDiT 单流层的 GEMM 在 6 张表里都排进前两名，所以减少去噪步数是最通用的方向；降低精度在 5090 上要配一个能吃满带宽的小 M kernel，在 Thor 上已经由 nvfp4 实现。
  2. 5090 nvfp4 的瓶颈不在 GEMM 算力，而在 kernel 效率（带宽只用到 25%）和量化开销（10.4%），这正是 5090 上 nvfp4 比 fp8 慢的原因。
  3. Thor nvfp4 的第 3 名已经是逐元素（1420 次启动，平均 5 µs），说明在 Thor 上，kernel 融合和减少启动次数比在 5090 上更值钱。

逐元素算子：组成、来源与优化

按模块（随上方精度切换）

为什么这么多，两台设备的瓶颈为什么不同

  • 次数主要来自 ActionDiT：每层 6–7 个，25 个 block × 10 步 = 250 次层执行，合计约 1,700 次启动，占逐元素启动总数的 80% 以上。
  • RTX 5090：受启动次数限制。以 fp16 为例（不含 fp8 的 compute_scale），ActionDiT 单流平均 1.4 µs/次，每个 kernel 只搬 0.4–1.5 MB，耗时基本就是启动和收尾的延迟。backbone 单流（M=416）每层 7 个 kernel 读写约 54 MB，20 层合计约 1.07 GB，却只用 0.65 ms；有效速率超过 DRAM 实测带宽，说明这些中间张量大多命中 L2。
  • Thor：受字节量限制。同样的 1.07 GB，backbone 单流用了 6.5 ms（fp16，140 次，47 µs/次），约 165 GB/s。ActionDiT 单流每层约 6.3 MB，200 次层执行合计 1.26 GB，用 7.1 ms，约 177 GB/s。两者都接近 Thor 实际能达到的带宽，不是启动延迟的问题。
  • 所以优化思路要分开看：在 5090 上要减少 kernel 个数；在 Thor 上要减少中间张量的写回和再读。融合 kernel 要是能同时去掉中间往返，两边都受益；只合并启动、字节量不变的改动，对 Thor 帮助很小。

为什么 fuse_qkv_norm_rope 必须实测

  1. 它内部用的还是旧 norm 的结构。这个融合 kernel 为每个 (row, head) 启动一个 256 线程的 block；HD=128 时只有 64 个线程在干活，而且每个 block 要做两次 256 宽的 block_reduce_sum，每次都带 __syncthreads。这和 vec_rms_norm 修掉的 rms_norm_kernel 是同一种结构；当初保留它，是为了和旧路径逐位一致（qkv_split_norm_rope_fp16.cu，kBlockThreads = 256）。
  2. 开关的对照组已经变了。现在默认是 vec_rms_norm（一个 warp 处理一行，不用 shared memory，也没有 block 级同步）。打开开关后，省掉的是"3 次拷贝 + 2 次 vec norm + 2 次 RoPE"，换来的是一个内部效率和旧 norm 相同的 kernel。净收益取决于这个 kernel 在各设备上能跑到多少带宽，没法只靠启动次数来推算。
  3. 两台设备上旧 norm 的代价差了 10 倍。5090 上旧 norm 是 4.3 µs/次（560 次共 2.4 ms），离上限不远；Thor 上是 41 µs/次（560 次共 23.0 ms），只跑到约 26 GB/s。融合 kernel 发出的 block 数和两次旧 norm 相同（rows × NH），每个 block 也做两次归约。
    • Thor 上，它替换掉的部分大约是 vec norm 的 2.7 ms，加上拷贝和 RoPE 约 9–10 ms（按约 1.6 GB 读写、约 170 GB/s 估算），合计约 12 ms。
    • 融合 kernel 本身：如果能跑到约 170 GB/s，约 6 ms（省约 6 ms）；如果像旧 norm 那样被结构卡住，接近 23 ms（反而慢约 11 ms）。
    • 实测落在后一种：融合 kernel 本身 19.7 ms，端到端慢 7–9.6 ms（见下方 Thor 表）。
  4. 数值：只对旧路径逐位一致，对当前默认不是。这个 kernel 和 256 线程的旧 norm 逐位一致（Thor 已确认 torch.equal）；但和 vec norm 的归约顺序不同（kernel 级 ≤1 ulp）。打开开关后，相对当前默认会有一个很小的数值差，这个差在整个网络里会放大。下表的对照组用来确认这个差全部来自归约顺序。

  2. 数值差全部来自归约顺序。② 证明 fused 和旧 norm 路径逐位一致；① 的偏差与 ③（vec 开/关）几乎相同（backbone cos 都是 0.998926 / 0.990500 / 0.999989）。也就是说，打开 fused 在数值上等于退回旧 norm，并没有引入新的误差。nvfp4 的 backbone cos 0.9905 看着偏低，但这个偏差在 vec_rms_norm 变成默认时已经接受过了（Thor 用真实 checkpoint 验证的 actions cos ≥ 0.99995）。
  3. Thor 上是净亏，不能设为默认。在 vec on 的默认配置上打开 fused，三档分别慢 7.2 / 7.0 / 9.6 ms，虽然同样少了 1670 个 kernel。② 逐位一致，说明 FA4 路径上的接线没问题；数值偏差和 ③ 相同，和 5090 一样。
  4. 原因在 block 结构，不在字节量。Thor 上每个 256 线程的 (row, head) block 固定花约 30 ns：prefill 每次约 8,300 个 block、283 µs，denoise 每次 1,536 个 block、44.7 µs。vec norm 处理同样的行只要每行约 2 ns。融合 kernel 本身就有 19.7 ms，已经超过它替换掉的拷贝 + norm + RoPE（≤18.8 ms）。相对旧的 256 线程 norm 它仍然省 11 ms（②），但相对 warp 版 norm 就亏了。
  5. 已改成每个 (row, head) 一个 warp，并设为默认：照抄 rms_norm_fp16_vec_warp_kernel 的 int4 加载和 warp_sum 顺序。改完后在 kernel 级、5 处层接线以及端到端输出上，都和 vec norm 默认路径逐位一致。
    • Thor：3 个独立进程、三档精度，共 9 个 A − B，全部在 +7.25 到 +8.25 ms 之间。融合 kernel 每次调用 prefill 50 µs、denoise 7.8 µs（256 线程版本是 283 / 44.7 µs）。
    • 5090：省 2.0–2.7 ms。
    • 现在由 frontend 的 setdefault 默认打开，上方各表是打开之前测的。

要点

  • 最快精度不同：5090 是 fp8（26.0 ms），Thor 是 nvfp4（87.3 ms），Thor 慢 2.9–4.6 倍。
  • 5090 fp8：attention、norm、逐元素和 absmax 合计 43%，和 GEMM 的 44% 相当；ActionDiT 占 58%。
  • Thor：GEMM 占 50–72%；非 GEMM 里最大的是逐元素（18–19 ms，约 13–17%），其次是 attention（FA4，约 9 ms）和 norm（约 8.2 ms）。
  • Thor fp8：GEMM 只比 fp16 快 1.56 倍，另有约 8 ms 花在 quant 和 absmax 上。
  • 和精度无关的部分（VAE、attention、norm、逐元素）：5090 约 12 ms，Thor 约 44 ms。
  • 5090 nvfp4：quant/cast 占 19.6%，是它比 fp8 慢的直接原因。
  • vec_rms_norm（现为默认）：5090 每次推理省 1.3–1.4 ms，Thor 省约 19 ms（norm 28.5 → 8.2 ms）。

范围与条件

  • 工作负载 ImageWAMWorkload.libero()：2 视角 224×224，horizon 64，10 步去噪；真实 LIBERO checkpoint 与 FLUX.2 AE；prompt 裁短后文本 24 token，图像 392 token，ActionDiT M=64。
  • 部署入口 load_imagewam 默认 profile，VAE 在 CUDA graph 内，vec_rms_norm 打开，fuse_qkv_norm_rope 关闭（测量时的默认值；之后已改为默认打开，5090 上 fp8 / nvfp4 / fp16 变为 23.85 / 28.23 / 32.88 ms）。attention：5090 为 cuBLAS QKᵀ/softmax/PV 链，Thor 默认 FA4（不是同一种算子）。
  • ImageWAM 没有 bf16 精度，16 位档是 fp16；fp8 为动态 scale。
  • 占比的分母是 eager kernel 合计（5090: 35.15 / 24.67 / 30.52 ms；Thor: 139.49 / 112.39 / 88.47 ms），与 infer() 实测相差在约 7% 以内。
  • backbone 入口投影并入"backbone 单流"，ActionDiT 输入输出投影与 Euler 并入"ActionDiT 单流"。"absmax"列：fp8 动态 scale 的 absmax（5090 含 memset，Thor 不含 0.26 ms memset）。
  • 5090：FlashRT 74b5efe，driver 595.91.07，torch 2.14.0+cu130，SM 时钟未锁定。Thor：MAXN，GPC 1.575 GHz，torch 2.9.1+cu130。
