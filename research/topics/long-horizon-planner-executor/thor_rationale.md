# Jetson Thor 上的规划器 + 执行器：问题、证据与工作项

本文件把长程规划–执行场景在 Jetson AGX Thor 上的工作串成一条链：目标指标 → 已测得的现状 → 三类 Thor 特有问题各自的证据与判断 →
每个工作项的目的、做法、预期与意义。数字都注明出处（`THOR_STATUS_SUMMARY.md` 的轮次、各实验目录的 README）；
推算与假设单独标出。执行状态见 `plan.md` 的 "Plan: Thor monitor-call latency, decision quality and co-location"。

## 1. 目标指标

**从调用开始到决策可用（L）**：harness 发起一次规划器调用（当前画面已拍下）到回复里 `action` 的值完整解码、可以解析
（它的右引号已生成）的墙钟时间。包含预处理（聊天模板、图像）、ViT、图像特征注入、前缀 capsule 恢复（复用时）、prefill、
解码到 `action` 闭合；不包含其后的 `reason` 文本与执行器切换指令的时间。

- 解码到 EOS 的做法里，harness 在回复结束后才解析 JSON，L 等于整次调用时间；"action 闭合即停"时 L 短于整次调用。
- 同步协议下机器人在 L 期间不动：等待占比 = L /（L + 检查间隔内的控制时间）。VoLoAgent 的 harness 每 80 个控制步（15 Hz）
  检查一次，控制时间 Δ = 5.33 s。
- 异步协议下 L > Δ 意味着下一次检查到期时上一次决策还没出来，调用堆积，且决策依据的画面已是 L 之前的。

三项约束，各对应一个受影响的对象：

| 约束 | 受影响的对象 | 量 |
|---|---|---|
| L < Δ，且越小越好 | 机器人（等待） | L 的中位与最大值；等待占比 |
| 执行器不错过控制截止期 | 执行器 | 执行器调用的 p99；超过截止期的比例 |
| 决策与原始路径一致 | 任务质量 | 干预决策（`replan`、`next`、工具动作）与参考的一致数 |

## 2. 现状（Jetson Thor，官方 Qwen3.8-27B NVFP4，monitor 调用，腕部 224）

| 路径 | L | 等待占比（推算） | 出处 |
|---|---|---|---|
| 原始：每次全部 prefill，解码到 EOS | 6.40 s | 55 % | `1110_h7h4bh8` H8 |
| 复用固定前缀 + action 闭合即停 | 2.61 s | 33 % | `1110_h7h4bh8` H8 |
| RTX 5090 同一提示词，原始 / 快路径 | 1.06 / 0.34 s | – | `experiments/monitor_call/README.md` |

- 5090 上原始路径已远低于 Δ；Thor 上原始路径高于 Δ（`1104_h3c` 回放 40 / 40 次超过）。L 超过间隔只在 Thor 上发生。
- 快路径的 2.61 s 里：prefill 约 2.0 s（77 %），解码约 0.45 s，ViT 与预处理约 0.15 s。
- Thor 相对 5090：prefill 13.8 倍，解码 3.6 倍（`1104_h3c`）。瓶颈从 5090 上的解码移到了 Thor 上的 prefill。
- Thor 的 prefill 有 55 % 在一个线性注意力 kernel 上：Thor 前端为了数值精度固定使用逐步递归的 `native` 后端，
  而不是 5090 的 WY 分块后端（WY 在 SM110 上逐层漂移，第 63 层 cos 0.43）；这一个 kernel 2 235 ms，是 5090 WY 路径
  69 ms 的 32 倍，同一次 prefill 里 fp4 GEMM 只是 3.8 倍（`1110_h7h4bh8` H4b，`opportunities.md` OPT-040 candidate 5）。
- 决策：快路径在 20 次调用上 action 全部不变，但这 20 次的参考决策全是 `continue`，干预决策尚未在 Thor 上检验。
- Thor 上同一提示词两次生成的回复只有 15 / 20 相同（5090 为 20 / 20），差异在 `reason` 文本或开头的 ```` ```json ```` 围栏
  （issues.md ISSUE-114）。

## 3. 三类 Thor 特有问题

延迟是结果；带宽与热态是 Thor 上影响延迟和执行器的两个机制。

### 3.1 延迟：真问题，主线

- 为什么 Thor 特有：只有 Thor 上 L 超过 Δ。
- 证据：第 2 节。快路径已把 L 压到 Δ 以下，但同步协议下仍有约三分之一的时间在等；剩余部分以 prefill 为主，
  而 prefill 最慢的一段是数值精度迫使的慢后端，不是未优化。
- 判断：继续压 prefill 是收益最大的方向；解码在闭合即停之后只剩约 0.45 s，不再是瓶颈。

### 3.2 带宽：真问题，需要共置实测

- 为什么 Thor 特有：两个模型共用一份统一内存（拷贝约 236–256 GB/s），按 SM 分区隔不开带宽。
- 证据（Thor）：8 个 SM 就能把拷贝带宽用满；SM 不相交时纯拷贝负载仍让执行器慢 1.80 倍（`1029`）；执行器变慢集中在与规划器
  解码重叠的调用上，为单独运行的 1.3–1.7 倍，与 prefill 重叠几乎不慢（`1030`）；green 分区下执行器 p99 高 21–41 %（`1028`）；
  规划器解码稳态约 200 GB/s，为拷贝上限的 85 %（`1104_h3c`）。
- 缺口：上述测量用的是替身规划器或纯拷贝负载；真实 27B 规划器与执行器按 harness 节奏共置尚未在 Thor 上测。

### 3.3 热态：在共置部署下大概率不是主要问题

- 现象：同一进程空闲 300 s 后，规划器解码每周期 138 ms（稳态 87.6 ms），约 50 s 后恢复；拷贝带宽只降 11 %；prefill 几乎不变
  （`1105_h6h4`，issues.md ISSUE-112）。
- 证据：空闲 5 / 15 / 30 / 60 / 120 s 都没有再现这一平台，120 s 之后只慢约 10 %（`1110_h7h4bh8` H7）；harness 的调用间隔只有几秒。
- 假设：与执行器共置时，执行器的周期负载让内存系统保持在快状态。未在 27B 规划器上验证。
- 判断：只留一个低成本测量收掉 300 s 的问题；共置时的热态并入带宽那一项一起看。

## 4. 工作项

### W1（H9）：让 WY 线性注意力后端在 Thor 上可用

- 目的：压缩快路径 L 里占 77 % 的 prefill。
- 做法：探针脚本对同一个 monitor 提示词逐层运行 WY 的五个阶段（kkt、solve_tril、recompute_wu、chunk_h、output_o），
  每个阶段的输出与 `native` 后端比 cos，先在 5090 上得到对照，再在 Thor 上定位漂移的阶段；之后修改那个阶段并测 prefill。
- 预期：漂移集中在一两个阶段。修好后若 WY 相对 5090 的倍数与 fp4 GEMM 相同（约 3.8 倍，约 0.27 s），monitor prefill
  从 3.98 s 到约 2.0 s，快路径 L 从 2.61 s 到约 1.6 s，等待占比约 23 %（推算，上限）。
- 风险：若漂移来自分块算法在 BF16 下的固有误差，该阶段需要 FP32，收益变小。
- 意义：Thor 的挑战不只是算力，而是数值精度迫使的慢路径；修复对 decompose 与 720 腕部图的长提示词（5.7k token）同样有效。

### W2（H11）：在含干预决策的调用上检验快路径

- 目的：让"快路径不改变决策"在需要干预的调用上成立。
- 做法：在 RTX 5090 上重跑闭环里的失败回合（任务 8 第 0 回合卡住、任务 0 第 1 回合认错物体等），录下 monitor 调用及图像，
  选出参考决策为 `replan` / `next` / 工具动作的调用；在 Thor 上用 `experiments/monitor_call/monitor_call_bench.py` 比较原始路径与快路径。
- 预期：对齐复用 + 闭合即停不改变干预决策（5090 上对齐复用与整段 prefill 逐 token 相同）；Thor 上的结论需扣除 W3 测得的运行间差异。
- 意义：5090 上的教训是近似手段让 `continue` 不变、却翻转了全部 3 次干预决策（`experiments/monitor_call/README.md` Finding 4）；
  只看 `continue` 的一致率看不出这种变化。

### W3（H12）：Thor 上运行间差异的大小

- 目的：得到 Thor 上回复比较的噪声底。
- 做法：同一调用在同一进程连续生成 5 次，记录首个不同 token 的位置与该处 top-2 logit 的差。
- 预期：差异出现在接近平局的位置（围栏、`reason` 的措辞），决策不变。
- 意义：W1、W2 以及任何 Thor 上的等价检查都要用它区分"改动造成的变化"与"运行间的变化"。

### W4：规划器进程，供 Thor 上的共置测量使用

- 目的：用真实 27B 规划器与快路径做共置测量。
- 做法：独立进程载入 Thor 图像前端，按 harness 节奏（每 5.33 s 一次 monitor）回放 66 次录制调用，原始与快路径两组，
  每次调用记录开始、决策可用、结束三个时间戳；运行前取得 Thor 上共用的 GPU 独占锁。执行器与共享方式由共置测量一方提供。
- 预期（假设）：执行器变慢集中在与规划器解码重叠的时段，快路径把每次 monitor 的解码从约 2.2 s 缩到约 0.45 s（推算），
  执行器 p99 与超过截止期的比例应随之下降；规划器在共置下的 L 由测量给出。
- 意义：若成立，同一改动同时缓解延迟与带宽争用，把 3.1 与 3.2 用一个机制连起来。

### W5（H10）：热态的 300 s 问题

- 目的：确认空闲 300 s 后的平台是否重现。
- 做法：`decode_cycle_drift.py` 空闲 180 s 与 300 s 交替各三次，每次空闲后背靠背 60 s。
- 预期：重现与否都不改变 3.3 的判断：部署中的调用间隔是秒级。
- 意义：对热态给出完整回答，使三类问题的结论都有直接证据。

## 6. 不在当前工作项里的方向

| 方向 | 理由 |
|---|---|
| 继续优化解码（MTP、K） | 闭合即停之后解码约 0.45 s，不是瓶颈 |
| 更多视觉复用 | 固定前缀（系统提示 + BEFORE 图）已全部复用；NOW 图每次不同 |
| RTX 5090 上的进一步优化 | 5090 上 L 已远低于 Δ |
| Thor 上的仿真闭环 | 当前执行器几乎不读指令（`experiments/sim_closed_loop/README.md` Finding 1），闭环体现不出分层的收益；价值在演示与 Thor 上的实际等待占比，先只做可行性检查（MuJoCo / robosuite 能否装进用户级环境） |
