Thor 上的规划器–执行器共置：导览

长时程任务、harness、统一内存硬件、推理优化与评估指标。快照 2026-11-18；† 表示未核实，「判断」表示推断。

主线：一块统一内存 SoC（Jetson AGX Thor）上，长时程规划器（HF 原版 Qwen3.8-27B）与周期执行器（约 4B 的 VLA/WAM）异步共置，同步协议作基线。 核心问题：两个时限都满足之后，规划器的决策延迟 L 怎样影响任务质量（SR、完成时间）？

1long horizon 在什么情况下出现

"子任务多"本身不够：CALVIN、LIBERO-Long 单段 ≤ 1 分钟且不需要记忆。需要规划器长上下文的，是下面几条叠加分钟级时长。

① 要回忆看不到的状态

遮挡物位置、计数、恢复原位，跨度到分钟级。代表：MemER 三任务（> 1000 帧）、MemoryBench、BEHAVIOR（平均 6.6 min）。

② 子任务多、episode 长

RoboCerebra 平均 9.1 个子任务、约 2 972 仿真步，约为已有数据集的 6 倍。CALVIN 每链 5 个，≤ 60 s。

③ 出错后重规划

重规划次数决定调用次数和 episode 长度，长度分布是长尾（判断）。代表：RoboCerebra 的随机扰动、VoLo 的 recovery。

④ 部分可观测的导航

路径长且方差大：VLN-CE 平均 55.9 个低层动作，RxR 上限 40 m。不压缩的视频历史随步数线性增长。

⑤ 多轮 agent 对话累积

工具返回留在对话里，每次检查重读全部历史。NavGPT-3 每 episode 155k–721k token。

3Thor 的硬件特点：CPU 与 GPU 共用一块内存

一块 DRAM，一条带宽

128 GB LPDDR5X，273 GB/s，CPU、GPU 与其他引擎共用。容量不再是瓶颈，带宽才是。

20 个 SM，粒度很粗

可以直接网格搜索 SM 分配。MIG 按 TPC 切（JetPack 7.2 实测 6 / 12 / 20 SM †），但不切内存。

SM 隔离不了带宽

按 SM 分开后，执行器剩下的干扰来自规划器 decode 的带宽占用。MIG 也只切计算，不切内存。

CPU 的内存流量也挤占 GPU

CPU 不占 SM，但它每读写一个字节都走同一条带宽。在 CPU 上注入满载的内存负载，规划器 decode 慢约 2.2 倍（B28）。

规划器 + 执行器的内存随上下文长度

规划器：Qwen3.8-27B NVFP4 权重 25.8 GiB + MTP 头 0.45 GiB + 线性注意力状态约 0.1 GiB，FP8 KV 每 token 32 KiB（16 层全注意力 × K/V × 4 头 × 256 维）。执行器：ImageWAM RoboTwin 权重 8.5 GiB。都按文件大小计，不含激活、workspace 与 CUDA graph。横轴为对数。

容量不是问题

上下文拉到模型上限 262k token，两个模型合计约 43 GiB，Thor 的 122 GiB 还剩一大半。同样的组合放不进 RTX 5090 的 31 GiB。

KV 的字节也不大

只有 1/4 的层有 KV，64k token 时 decode 每步多读约 2 GiB，比权重的约 15 GB 小得多。瓶颈要看时间，见下图。

关思考：瓶颈是 prefill

回复 15–650 token，1k 上下文时整次调用 1–5 s；4k 以上主要是 prefill，16k 约 11–28 s，32k 约 27–30 s。约 9k token 时单是 prefill 就超过 Δ。

开思考：一次调用要 1–3 分钟

思考长度 1 100–3 300 token，12 次里有 5 次到 4 096 上限仍未想完。即使 1k 上下文，整次调用也要 61–101 s，是 Δ 的 11–19 倍。解码 25–44 ms/token，随上下文变长。

Thor 上长解码的一个坑：graph 缓存上限

FlashRT 按解码位置录制 CUDA graph，默认最多缓存 256 张。解码超过约 750 token 后旧 graph 被挤掉、反复重录，每 token 从约 30 ms 变成约 100 ms。把上限调到 8 192 后恢复。64k 以上 decode 约 100 ms/token 是另一个问题（ISSUE-117），调大缓存无效。

4Thor 上特有的推理优化

先看数据怎么从 CPU 到 GPU：独立显卡要跨一条慢总线，统一内存没有这条总线，但所有流量都挤在同一条 273 GB/s 上。

5090 显存带宽与 PCIe 5.0 为官方规格；Thor 从 CPU 到 iGPU 支持硬件全一致（CUDA for Tegra 应用说明 §3.2），这是零拷贝高效的前提。

四类优化选项

① 数据进出：省掉拷贝

  • 零拷贝：CUDA 本身提供（pinned 或 managed 内存），但 FlashRT 没有用，输入仍走 cudaMalloc + 拷贝。要用就得手动改输入路径，省掉一次 DRAM → DRAM 拷贝。
  • 前缀状态和记忆快照可以多存几份，不再受显存容量限制。
  • 分配方式要实测：MI300A 上同一块内存，GPU 带宽可差 35 倍；llama.cpp 的 iGPU 零拷贝因输出损坏已关闭。

输入只有 MB 级，单次收益小，优先级靠后。

② 规划器：每次调用少读少算

  • 低比特：NVFP4 权重 + FP8 KV 已有
  • 推测解码：线性 MTP 已有；树状 MTP 没有，TRT Edge-LLM 在 Thor 上 14.68 ms/token。
  • 少做 prefill：固定前缀复用、决策闭合即停 已有；按帧缓存 ViT 输出 没有：MemER 每次约 16 帧，相邻两次调用大多是同一批帧，只需对新帧跑 ViT。

monitor 调用已从 6.40 s 降到 1.77 s，剩下的大头是 prefill。

③ 共置：两个模型和 CPU 怎么分带宽

  • 分 SM：20 个 SM 直接网格搜索；轮换几种配置，近似非整数的分配。
  • 运行中动态调 SM：按执行器余量做负反馈，余量大就把 SM 让给规划器，余量小就收回（机制见下表）。
  • 优先级与让步：MPS 客户端优先级（实测执行器 0 % 错过）；按执行器余量暂停规划器 decode 或缩小推测树。
  • CPU 负载预算：CPU 算力空闲可用，但它的内存流量计入同一预算；满载时规划器 decode 慢约 2.2 倍。

约束：改 prefill 分块边界会改变规划器决策，让步只能放在分块边界上。

④ 硬件旋钮（需要 sudo）

  • MIG：按 TPC 切成 6 / 12 / 20 SM †，只切计算，不切内存。
  • 时钟：nvpmodel 功耗模式，GPU 与内存（EMC）时钟。
  • 内存控制器节流或 QoS：RT-Gang++ 在 Jetson Nano 上用过，Thor 上是否开放待查 †。

这些设置作用于整块板，要和同板的其他实验错开时间。

6两个时限都满足后，怎样给系统排序

余量只是门槛，不是目标。门槛之上用什么排序，取决于 L 对质量的影响是哪种形状。

示意，比例不准。同步时执行器在 L 期间停下；异步时执行器继续按旧子任务走。门槛一：执行器每次推理 < 200 ms；门槛二：L < Δ。

两个余量现在有多大

余量单独运行共置（MPS 客户端优先级）再加 CPU 内存负载来源
执行器：200 ms − p99162 ms（37.5 ms）130 ms（p99 70 ms）约 60 ms（p99 约翻倍）ImageWAM 动作模型，Chenwei B27 / B28
规划器：Δ − L，VoLo 节奏（Δ = 5.33 s）3.56 s（L = 1.77 s）2.8 / 0.3 s（p95 2.5 / 5.0 s，腕部 224 / 720）decode 慢约 2.2 倍本组 Thor 实测；B27 / B28
规划器：Δ − L，MemER 节奏（Δ ≈ 1 s）约 −1 s（L ≈ 2 s）< 0< 0推算：MemER 约 1 Hz；2k token prefill 1.1 s + 30 token 解码 0.9 s

执行器的余量很大

即使共置再加 CPU 内存负载，ImageWAM 动作模型的 p99 仍离 200 ms 有约 60 ms。单纯"保护执行器"不是紧约束。

规划器的余量小，甚至为负

VoLo 节奏下腕部 720 只剩 0.3 s；换成 MemER 的约 1 Hz，现有 L 已经超过 Δ，开思考更远。紧的是规划器这一侧。

所以目标是：在执行器余量 > 0 的前提下压低规划器的 L

执行器用不完的余量，应该通过 SM 和带宽让给规划器。这也是动态调 SM 的意义。

异步协议下延迟与成功率：已发表的数据点

只收原文表格里的数字。横轴是推理延迟 d（控制步）：A2C2 与 VLASH 都没有写明一步多少毫秒，所以不换算成 ms。圆点为 Kinetix，方块为 LIBERO；橙色为朴素异步，蓝色为带延迟补偿的异步（RTC、A2C2、VLASH）。悬停可看来源。

数据点全部来自执行器层

延迟最多 10 个控制步，都是动作块的推理延迟。规划器层面没有一组可用的"L 与 SR"数值：MemER 只说 10–15 s 的 API 规划器"完全失败"，NavGPT-3 报的是修复用时而不是推理时延。

带延迟补偿的异步几乎不受延迟影响

A2C2 在 Kinetix 上 d = 0–4 都在 86.5–88.9 %，VLASH 在 LIBERO 上 d = 0–3 在 94.6–97.2 %。朴素异步在 Kinetix 上从 88.9 % 掉到 51.2 %。

异步协议的四个维度

维度选项执行器层（动作块）规划器层（子任务）
① 何时发起下一次推理周期 / 队列见底 / 事件触发SmolVLA：剩余动作低于阈值 g 就发新观测MemER：上一次结束立刻发下一次；VoLo：0.2 Hz 周期，出错时事件触发；Tri-System：Critic 判定完成或失败才唤醒
② 新结果何时生效立即替换 / 等到边界 / 平滑拼接朴素异步：新动作块到了直接替换Hi Robot、MemER、Helix、DualVLN：写进"最新值"，执行器下次读取时生效
③ 是否补偿推理期间的延迟不补偿 / 冻结已承诺的部分 / 用最新观测修正 / 预测执行时刻的状态朴素异步不补偿；RTC 冻结推理期间要执行的动作，只补全后面的；A2C2 每步用最新观测做小修正；VLASH 用上一个动作块把机器人状态推到执行时刻再推理MemER 训练时把子任务标签往后挪约 0.5 s，让规划器预测略未来的子任务；其余基本不补偿
④ 能否打断正在执行的不可打断 / 优先级中断一般不打断NavGPT-3 的 overlap + priority；VoLo 的 recovery 会停下执行器

决定曲线形状的是第 ③ 维

不补偿的朴素异步在 Kinetix 上从 88.9 % 掉到 51.2 %；RTC、A2C2、VLASH 做了补偿，曲线平得多。

规划器层几乎没有补偿

执行器层的补偿已经很成熟，规划器层只有 MemER 的标签平移。让规划器知道自己的 L、或用最新观测修正旧决策，是一个空白。

实验里这几个维度都是变量

至少比较同步、朴素异步、带补偿的异步三种，在不同的 L 下看 SR 曲线的形状。

时延常常先体现在用时上

Fast Plans 和 SmolVLA 的成功率基本不变，用时和动作时间占比变化很大。只看 SR 会漏掉时延的代价。

我们的排序思路（判断）

第一步：画出 SR 与完成时间随 L 的曲线

在 RoboCerebra 上按仿真时间，固定调用周期，注入不同的 L，异步与同步各一条。曲线的形状决定用哪种指标。

门槛型 → 比能力

比在两个余量都 > 0、且 SR 不低于目标时，能支持的最小 Δ、最长上下文或最大 CPU 负载。这是 goodput 的直接翻译。

连续型 → 比 SCT

用 SCT 或 throughput 这类"成功率 × 时间效率"的单一分数。系统优化把 L 降下来，分数就应该升。

评估要对齐

主指标就是"实际 vs 理想"图里的那个量。理想值：规划器独占时的 L，执行器独占时的时延。
